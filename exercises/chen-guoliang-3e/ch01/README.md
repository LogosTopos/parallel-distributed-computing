## 1.6 向量点积的峰值性能

**题意。** 处理器主频为 1 GHz，L1 容量为 32 KB，DRAM 容量为 512 MB；L1 访问延迟为 1 个时钟周期，DRAM 为 100 个时钟周期。每个存取周期取出 4 个字，即缓存行包含 4 个字。问向量点积可以获得的峰值性能。

### 从数据搬运量到浮点运算量

考虑点积 $s=\sum_{i=1}^{n}a_i b_i$。每处理一对元素，需要读取 $a_i,b_i$，并进行一次乘法和一次加法。按常用性能计数约定，工作量取 $2n$ FLOP；若只计算数学表达式所需的运算，则是 $n$ 次乘法和 $n-1$ 次加法，这一差别不影响大规模点积的结论。FMA 即使作为一条指令执行，也按 2 FLOP 计。

采用本题的简化模型：每个向量元素占一字、顺序访问时一行中的 4 个字都能用到、累加器保存在寄存器中、暂不计最终写出一个标量的开销。于是点积每读入 2 字完成 2 FLOP，运算强度是 **1 FLOP/字**。

主频 1 GHz 对应时钟周期 1 ns，因此：

| 数据供给层次 | 每次访问耗时 | 每次返回数据 | 数据供给速率 | 点积的访存限制上界 |
| --- | --- | --- | --- | --- |
| L1 命中 | 1 ns | 4 字 | $4\times10^9$ 字/s | **4 GFLOPS** |
| DRAM | 100 ns | 4 字 | $4\times10^7$ 字/s | **40 MFLOPS** |

也可以按整段点积计算：两个向量共需 $2n$ 字，约访问 $n/2$ 个缓存行。若每行耗时 $L$ 秒，则总访存时间约为 $nL/2$，性能为 $2n/(nL/2)=4/L$ FLOPS。

### 容量和“峰值”的含义

32 KB 决定两个向量能否同时留在 L1 中。若每字为 $w$ 字节，且将容量按 32 KiB 解释，忽略其他数据占用，容量条件为 $2nw\leq32768$：4 字节元素对应 $n\leq4096$，8 字节元素对应 $n\leq2048$。这只是容量上的必要条件，实际还受缓存映射等因素影响。

小向量已经装入 L1、之后重复计算时，可以使用 L1 一栏；首次从 DRAM 读取的冷启动计算仍需付出装入代价。大向量的工作集超出 L1、需要持续从 DRAM 搬运时，应使用 DRAM 一栏。512 MB 主要约束可容纳的数据规模，不直接出现在上述速率公式中。若一个元素实际占多个字，则需相应降低 FLOP/字，不能照搬表中结果。

**4 GFLOPS 和 40 MFLOPS 是题设模型给出的访存限制上界。** 只给主频并不能确定浮点运算单元每周期能完成多少运算；实际性能还不超过处理器的算术吞吐上限。此外，这里将题给的“每个存取周期取 4 字”理解为请求不重叠的服务模型。对允许多个请求并行、流水供数的真实存储系统，单次访问延迟不足以单独推出峰值带宽。

程序中的计算是对题设公式的数值复现，不是本机点积测速：

```text
[1.6] dot product, one word/element, 2 FLOP/pair
L1: 1 ns/access, 4000000000 word/s
dot-product memory ceiling: 4000 MFLOPS
DRAM: 100 ns/access, 40000000 word/s
dot-product memory ceiling: 40 MFLOPS
```

## 1.7 DSM 的有效访存时间

**题意。** 分布共享计算平台中，本地缓存、本地内存和远程内存的访问时间分别为 10、100、400 ns。负载均衡；80% 的访问命中本地缓存，10% 访问远程内存。求有效访存时间，以及内存受限时的峰值计算速度。

DSM 在这里指 **Distributed Shared Memory，分布共享存储**：物理内存分布在不同节点，但程序可通过共享地址空间访问。数据在本地还是远程，会影响访问代价。

剩余 10% 的访问落在本地内存。三种情况互斥且覆盖全部访问，把题给的时间看作每种访问的总成本，取加权平均：

$$
T_{\mathrm{eff}}=0.8\times10+0.1\times100+0.1\times400=\boxed{58\ \mathrm{ns}}.
$$

这里的 10% 远程访问占全部访问的 10%，不是缓存未命中之后的条件概率。如果 100、400 ns 表示缓存检查失败后再增加的罚时，公式会不同；本题按三种完整访问时间解释。

在访存不能重叠的模型下，每个处理器的访问速率上界为 $1/(58\times10^{-9})\approx1.72414\times10^7$ 次/s，即 **17.24 M 次访存/s**。

按“每次访存支持一次浮点运算”的简化口径，峰值计算速度为 **17.24 MFLOPS**。严格地说，内存受限并不自动说明每次运算需要多少次访存：若平均每次浮点运算需 $a$ 次这样的访问，上界应为 $17.24/a$ MFLOPS。题目没有给处理器数量，因此这也不是整个并行系统的总 FLOPS；负载均衡本身不能提供缺失的处理器数或互连带宽。

远程访问虽然只有 10%，却在每次平均访问中贡献 40 ns，占总时间的 $40/58\approx69.0\%$。因此，负载均衡之外，还应关心数据放在哪里、任务由哪个节点执行。

```text
[1.7] effective access time
average = 58 ns, rate = 17.241379 Maccess/s
one access/operation: 17.241379 Mop/s
```

## 后三题的共同约定

同一个共享地址可以在多个处理器的私有缓存里保留副本。要解释题图，应分别问：**最新值在哪里？这次读取会从哪里取值？**

| 名称 | 英文 | 规则或含义 |
| --- | --- | --- |
| 写直达 / 写通 | Write-through，WT | CPU 写缓存时，也把该次更新传到下层存储；本实验令写入立即完成 |
| 写回 | Write-back，WB | CPU 先修改缓存，记录尚未写回的修改，稍后再更新下层存储 |
| 脏数据 | Dirty data | 含有尚未写回下层存储的修改，不表示数据错误 |
| 写更新 | Write-update | 某 CPU 写入后，将新值传播给其他仍有效的缓存副本 |
| 写无效化 / 写无效 | Write-invalidate | 某 CPU 写入时，使其他缓存副本失效；之后读取必须重新取得有效数据 |
| DMA | Direct Memory Access | 设备直接与内存交换数据；题 1.9 假设这条路径不参与缓存一致性维护 |

WT/WB 规定对下层存储的写入时机，写更新/写无效化规定如何处理其他缓存。它们不是四个互斥的选项，WB 可以与写更新或写无效化分别组合。

以下程序按确定顺序执行一个操作，再执行下一个；所有处理器访问同一个地址。`None` 表示该缓存没有有效副本，输出中记为 `I`；`*` 表示脏副本。题 1.8、1.9 刻意使用**没有一致性机制**的模型，以复现题图中的问题。

这是一段显式维护“主存值”和“缓存值”的串行模拟程序，不是让 Python 线程实际绕过 CPU 的缓存协议。每步都执行完再进入下一步，所以出现旧值无需借助数据竞争、线程调度或运行时机的偶然性。

## 1.8 进程迁移为什么会读到旧值

**题意。** 结合图 1.20，说明 WT 下进程从 $P_2$ 迁移到 $P_1$，以及 WB 下包含共享变量 $X$ 的进程从 $P_1$ 迁移到 $P_2$，为什么可能造成缓存不一致。

### WT：主存已经更新，目标处理器仍命中旧副本

先让 $P_1$ 缓存 $X$。进程在 $P_2$ 上把它改成 $X'$；WT 将主存同步改成 $X'$，但单靠 WT 不会替 $P_1$ 更新旧缓存。此后进程迁移到 $P_1$，对该地址的读取命中本地缓存，返回旧值 $X$，根本没有访问已更新的主存。

| 步骤 | $P_1$ 缓存 | $P_2$ 缓存 | 主存 | 读取结果 |
| --- | --- | --- | --- | --- |
| $P_1$ 曾经读取 | $X$ | I | $X$ | $X$ |
| $P_2$ 写入 $X'$，采用 WT | $X$ | $X'$ | $X'$ | — |
| 进程迁移到 $P_1$ 并读取 | $X$ | $X'$ | $X'$ | **旧值 $X$** |
| 使 $P_1$ 旧副本失效后重读 | $X'$ | $X'$ | $X'$ | 新值 $X'$ |

对应的最小调用如下。代码中的处理器编号从 0 开始，`0` 对应 $P_1$，`1` 对应 $P_2$。

```python
m = NoCoherence("WT")
m.read(0)           # P1 留下旧副本
m.write(1, 1)       # P2 写新值，同时更新主存
print(m.read(0))    # 迁移到 P1 后仍读到 0
m.invalidate(0)
print(m.read(0))    # 重新取主存，得到 1
```

### WB：最新值留在原处理器，目标处理器从旧主存装入

$P_1$ 把 $X$ 改成 $X'$，采用 WB 后最新值只留在 $P_1$ 的脏缓存中，主存还是 $X$。进程迁移到 $P_2$ 时，$P_2$ 没有该地址的缓存副本，便去主存取数，得到旧值 $X$。

| 步骤 | $P_1$ 缓存 | $P_2$ 缓存 | 主存 | 读取结果 |
| --- | --- | --- | --- | --- |
| $P_1$ 写入 $X'$，采用 WB | $X'$，脏 | I | $X$ | — |
| 进程迁移到 $P_2$ 并读取 | $X'$，脏 | $X$ | $X$ | **旧值 $X$** |
| 写回 $P_1$，使 $P_2$ 旧副本失效后重读 | $X'$ | $X'$ | $X'$ | 新值 $X'$ |

```python
m = NoCoherence("WB")
m.read(0)
m.write(0, 1)
print(m.read(1))    # P2 从尚未更新的主存读到 0
m.clean(0)         # 将 P1 的新值写回主存
m.invalidate(1)    # 前一步错误读取已经让 P2 缓存了旧值
print(m.read(1))    # 得到 1
```

两种情况分别对应“命中旧缓存”和“未命中后读取旧主存”。**只修复其中一条路径还不够。** 在第二个例子中，只做 `clean(0)` 仍不能修复已经进入 $P_2$ 的旧副本。

实际运行输出：

```text
[1.8] WT, migrate P2 -> P1
after P2 writes 1: P1=0, P2=1, Mem=1
migrated process reads on P1: 0 (expected 1)
after invalidating P1: 1
[1.8] WB, migrate P1 -> P2
after P1 writes 1: P1=1*, P2=I, Mem=0
migrated process reads on P2: 0 (expected 1)
after clean P1 + invalidate P2: 1
```

进程迁移改变的是运行它的处理器，并不意味着原处理器的所有缓存行自动搬到新处理器。题图说明了为什么需要一致性机制，不能据此断言具备正确一致性机制的机器采用 WT/WB 就一定在迁移时读错。

## 1.9 绕过缓存的 I/O 为什么也会读错

**题意。** 结合图 1.21，解释两种情况：① 设备将新数据 $X'$ 写回主存，但绕过采用 WT 的 CPU 缓存；② 设备直接从主存输出数据，但 CPU 使用 WB，最新数据尚未写回。

### 输入方向：设备已经写好，CPU 却保留旧副本

这里“输入”指设备把数据送入主存。例如，两个 CPU 都缓存了值 0，设备通过不参与一致性的 DMA 路径把主存改成 1。CPU 再读取该地址，仍可能命中本地缓存中的 0。

WT 的作用范围是 **CPU 发起的写入**。它并不反过来保证“设备写主存时，所有 CPU 缓存都被更新”。因此，本例中必须在设备写入完成后、CPU 重新使用缓冲区前，使相关旧缓存失效，或由硬件一致性机制完成等价工作。

```python
m = NoCoherence("WT")
m.read(0)
m.read(1)
m.dma_write(1)     # 设备绕过 CPU 缓存，直接写主存
print(m.read(0))   # 0
m.invalidate(0)
m.invalidate(1)
print(m.read(0))   # 1
```

本题采用 WT，示例中的旧 CPU 副本是干净的，可以丢弃。对一般 WB 缓冲区，不能在不处理脏数据的情况下随意丢弃缓存，也不能在设备写好之后再把旧的脏缓存写回去覆盖它；必须安排好 CPU 与设备对缓冲区的使用阶段。

### 输出方向：CPU 已经写好，设备却读取旧主存

这里“输出”指设备从主存取数据送往外部。CPU 在 WB 缓存里把 0 改成 1，但主存仍为 0。设备绕过缓存从主存取数，自然取得 0。应当在设备开始读取前，将 CPU 的相关脏缓存写回主存，或使用能够取得最新缓存数据的一致性 I/O 路径。

```python
m = NoCoherence("WB")
m.write(0, 1)
print(m.dma_read())  # 0
m.clean(0)          # 先完成写回，再交给设备
print(m.dma_read())  # 1
```

完整演示还保留了 $P_2$ 的旧副本，以说明**修好设备的读取路径，不等于修好了所有 CPU 的读取路径**：

```text
[1.9] DMA input with WT
after device writes 1: P1=0, P2=0, Mem=1
CPU reads: P1=0, P2=0 (expected 1, 1)
after invalidation: P1=1, P2=1
[1.9] DMA output with WB
after P1 writes 1: P1=1*, P2=0, Mem=0
device reads: 0 (expected 1)
after cleaning P1, device reads: 1
P2 still reads: 0 (CPU coherence is a separate issue)
```

在真实 Linux 驱动中，应使用 DMA 映射与同步接口来表达 CPU/设备间的缓冲区交接，例如适用场景下的 `dma_sync_single_for_cpu()` 和 `dma_sync_single_for_device()`，而不是照搬这里的 Python 方法。是否需要缓存维护、执行哪些动作，由具体平台和映射类型决定；CPU 与设备也不能在未协调的阶段随意同时修改缓冲区。参见 [Linux DMA 官方指南](https://www.kernel.org/doc/html/latest/core-api/dma-api-howto.html)。

## 1.10 WB 下的写更新和写无效化

**题意。** 结合图 1.22，解释采用 WB 的写更新和写无效化协议如何维护一致性。图中的 $X$ 为旧副本，$X'$ 为新副本，I 表示无效。

### 写完成时，各副本应该是什么状态

先让三个处理器都缓存 $X$，主存也保存 $X$，然后令 $P_1$ 写入 $X'$。两种策略得到：

| 时刻或策略 | $P_1$ | $P_2$ | $P_3$ | 主存 |
| --- | --- | --- | --- | --- |
| 写入之前 | $X$ | $X$ | $X$ | $X$ |
| WB + 写无效化，写完成后 | $X'$ | I | I | 旧值 $X$，不能直接作为最新数据响应 |
| WB + 写更新，写完成后 | $X'$ | $X'$ | $X'$ | 旧值 $X$，不能直接作为最新数据响应 |

图中主存位置的 I 应理解为：**这份旧数据不再具有提供最新值的资格**。不是主存里的比特消失了，也不是所有实际机器都给 DRAM 配置与 CPU 缓存相同的 I 状态位。协议必须另行记录最新数据由谁负责。

**写无效化的过程：** $P_1$ 发出写入/独占请求，其他持有旧副本的缓存监听到请求后将对应行置为无效；完成必要的协调后，$P_1$ 可以写入。后续 $P_2$ 再读时发生未命中，必须通过协议取得新值 $X'$，不能直接从仍旧的主存取 $X$。

**写更新的过程：** $P_1$ 写入时传播新值，其他持有该缓存行的有效副本也更新为 $X'$。后续 $P_2$ 读取可以直接命中。因为仍然采用 WB，更新其他缓存不要求这一步同时更新主存。没有该行的缓存无需因广播而强行装入一份副本。

### 玩具模型如何找到最新值

`CoherentWB` 在每次写入后记录 `owner`，表示哪个处理器负责尚未写回的最新值。读未命中时，如果存在 `owner`，就从它的缓存取数；否则才从主存读取。这是为了把“主存已旧，但系统仍能正确读”的原因直接写进代码。

```python
def read(self, cpu):
    if self.cache[cpu] is None:
        self.stats["misses"] += 1
        if self.owner is None:
            self.cache[cpu] = self.memory
        else:
            self.cache[cpu] = self.cache[self.owner]
            self.stats["cache_transfers"] += 1
    return self.cache[cpu]
```

写入时，两种策略的差别只在如何处理其他有效副本；下面截取了程序中的对应分支：

```python
if peers:
    if self.policy == "update":
        self.stats["updates"] += 1
        for i in peers:
            self.cache[i] = value
    else:
        self.stats["invalidations"] += 1
        for i in peers:
            self.cache[i] = None
self.cache[cpu] = value
self.owner = cpu
```

`write()` 在进入这段代码之前，会先通过 `read(cpu)` 取得有效副本。因此，即使换成另一个处理器写入，尚未写回的最新版本也不会因为旧所有者失效而丢失；最后由新写者接管写回责任。`writeback()` 将所有者的值写入主存，并清除这份未写回责任。

该模型允许所有者在向其他缓存供数后继续承担写回责任。它演示书图所需的策略，不宣称实现了完整的 MSI、MESI 或 Dragon 协议；实际协议还要明确稳定状态、过渡状态、请求、确认与竞争处理。例如 [gem5 的 MSI 示例](https://www.gem5.org/documentation/learning_gem5/part3/cache-intro/) 使用 M、S、I 状态和显式消息状态机，不能仅凭本模型的 `owner` 字段把它等同于 MSI。

### 一次写入和一次读取的运行结果

```text
[1.10] WB + invalidate
before write: P1=0, P2=0, P3=0, Mem=0, owner=none
after P1 writes 1: P1=1, P2=I, P3=I, Mem=0(stale), owner=P1
P2 reads: 1
after P2 reads: P1=1, P2=1, P3=I, Mem=0(stale), owner=P1
after writeback: P1=1, P2=1, P3=I, Mem=1, owner=none
events: {'updates': 0, 'invalidations': 1, 'misses': 1, 'cache_transfers': 1, 'writebacks': 1}

[1.10] WB + update
before write: P1=0, P2=0, P3=0, Mem=0, owner=none
after P1 writes 1: P1=1, P2=1, P3=1, Mem=0(stale), owner=P1
P2 reads: 1
after P2 reads: P1=1, P2=1, P3=1, Mem=0(stale), owner=P1
after writeback: P1=1, P2=1, P3=1, Mem=1, owner=none
events: {'updates': 1, 'invalidations': 0, 'misses': 0, 'cache_transfers': 0, 'writebacks': 1}
```

写无效化下，$P_2$ 的读未命中触发一次缓存间供数；写更新下，$P_2$ 直接命中。两种情况下都读到 1，尽管在显式写回之前主存始终为 0。`stale` 表示主存当前不应被当作权威数据源；真正需要维护的是读操作得到正确版本，而不是每一时刻让主存和所有缓存都保存相同的比特。

## 补充实验：哪种策略更合适，取决于访问顺序

让三个处理器先读入 0，然后把计数器清零。所有写操作由 $P_1$ 发起，依次写入 1、2、3；比较两种模式：

1. **连续写后再读（burst）：** $P_1$ 连续写三次，最后 $P_2,P_3$ 各读一次。
2. **每次写后都读（interleaved）：** $P_1$ 每写一次，$P_2,P_3$ 随即各读一次，然后才发生下一次写。

实际输出中的计数整理如下：

| 访问模式 | 策略 | 更新广播 | 无效化广播 | 读未命中 | 缓存间供数 |
| --- | --- | ---: | ---: | ---: | ---: |
| 连续写后再读 | 写更新 | 3 | 0 | 0 | 0 |
| 连续写后再读 | 写无效化 | 0 | 1 | 2 | 2 |
| 每次写后都读 | 写更新 | 3 | 0 | 0 | 0 |
| 每次写后都读 | 写无效化 | 0 | 3 | 6 | 6 |

一次广播不论有几个接收缓存，都只计一次；一次缓存间供数表示一次读请求从所有者取得数据。统计窗口不包含预热，也不包含最终写回。此窗口结束时，四次实验的主存都仍为 0，而三个处理器通过协议都能读到最新值 3。

连续写的场景里，写更新传播了没有人读取的中间值 1 和 2。写无效化只在第一次写时使两个读者的副本失效，随后两次写可以留在本地，读者最后再取得值 3。但表中还包含最后两次供数，因此不能只比较“3 次更新”和“1 次无效化”就断言总耗时相差三倍。

每次写后都读的场景里，每一版新值都有人使用。写更新让读者直接命中；写无效化则反复引起失效和重新取数。这个例子显示了及时传播新值的收益。

这些是**模型事件数，不是真实硬件运行时间或总线字节数**。更新广播携带数据，无效化广播主要携带地址和控制信息；缓存间供数又可能传送整行。真实代价还取决于缓存行大小、读写粒度、拓扑和并发情况，不能把各类计数无权相加当作性能。
